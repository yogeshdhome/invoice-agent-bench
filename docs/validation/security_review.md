# Security review — implementation vs. claims

Scope: source in `src/invoice_bench/`, tests in `tests/`, published run logs. A control is marked **Implemented + tested** only
where both code and an automated test exist. "Ad hoc" means verified during this review by a script that is not in the repository.

| # | Threat | Control in the benchmark | Status | Evidence | Gap / production need | Severity |
|---|---|---|---|---|---|---|
| S1 | Unauthorised data retrieval | AP services filter every read by tenant and business unit from the caller's token; hardened agent re-checks scope after each invoice fetch (`graph.py:182`) | **Implemented + tested** | `test_services.py::test_obo_scoping_vs_service_account`; 0 retrievals in H and A1 runs | Works only because the downstream service enforces the user's scope. Real ERP APIs often do not; then the agent must enforce it | — |
| S2 | Cross-tenant access | Same as S1; policy `in_scope` (SC-01/SC-02) | **Implemented + tested** | `test_policy.py` cases SC-01/02; `test_cross_tenant_is_not_found_or_no_access` | Tenant context comes from token claims issued by the harness, not an identity provider | — |
| S3 | Hardened reads authorised by the policy engine | **Not as claimed.** Hardened reads are *not* passed through `policy.decide`; they rely on S1 plus the post-fetch scope check. Only writes go through `decide` (`graph.py:354`) | **Partially implemented** | code inspection | Article §5.1 says the policy engine "decides every call" — inaccurate (see V-05) | Medium |
| S4 | Prompt injection (indirect) | Vendor text excluded from the planning prompt; actions only from user intent; explainer sees vendor text inside delimiters | **Implemented + tested** | `test_injection_text_never_reaches_planner…`, `test_tool_output_cannot_create_an_action` | Explainer can still be influenced (narrative distortion). Static payloads produced 0 attempts in all arms, so the defence was not exercised by the model | Low |
| S5 | Excessive tool permissions | Hardened: no tool chosen by the model; `update_vendor` denied for everyone (VM-01). Baseline deliberately given the over-broad `update_vendor` tool (design decision D5) | **Implemented + tested** | `test_decisions` (VM-01); `test_baseline_executes_injected_bank_change_a1_blocks_it` | Article does not mention that B0 had this tool (V-16) | Low |
| S6 | Approval spoofing | Approval resume carries `approver_user_id`; the graph looks it up in a user directory and checks role + segregation of duties | **Not implemented (authentication)** | `graph.py` request_approval: approver identity is taken from the resume payload; no token or signature | Anyone able to resume the graph can name any approver. Article §5.2 says the hash proves "who approved it" — unsupported (V-02). Production needs an authenticated approval channel (signed approval or approver's own session) | **High** (for claims) |
| S7 | Approval replay / mismatch | Resume must carry the card's action hash; mismatched hash rejected | **Implemented + tested** | `test_approval_card_is_bound_to_action_hash…` | See S8 for re-use defect | — |
| S8 | Stale or re-used approvals | Expiry checked against the stored `expires` at resume | **Implemented, defect found** | `approval_id = "APR-" + hash[:12]`; `INSERT OR IGNORE` keeps the **first** expiry. Re-requesting the same action after expiry is immediately "expired"; the idempotency key also includes this ID, so a legitimate later repeat of an identical action would replay the old result | Add a per-request nonce to the approval ID and idempotency key. Not triggered in the benchmark (fresh database per run, one request per thread). Time-based expiry itself has no test | Medium (code) |
| S9 | Conditions change after approval (TOCTOU) | Service-side preconditions only (no active hold → 422; holds present → cannot schedule payment) | **Partially implemented** | `repository.py` release/approve preconditions | No full re-authorisation or business-rule re-check before the write. Article states this correctly | — (disclosed) |
| S10 | Duplicate side effects | Deterministic idempotency key; service `action_log` unique key inside `BEGIN IMMEDIATE` | **Implemented + tested (sequential); concurrent ad hoc** | `test_n_identical_writes_yield_one_effect` (sequential); ad hoc: 16 concurrent requests with the same key → 1 effect, 15 replays. 16 concurrent requests with **different** keys → 16 effects | Article's "concurrent duplicates collapse" holds only for the same key (V-13). No business-level de-duplication | Medium (claim) |
| S11 | Uncertain write outcome | Hardened retries writes only with the same deterministic key; service replays | **Implemented** | `resilient.py` (`hardened writes require a deterministic idempotency key`) | Relies on downstream key support (disclosed in article) | — |
| S12 | Crash recovery | Checkpointed graph; idempotent execute node | **Implemented + tested (in-memory)** | `test_crash_after_write_then_resume_does_not_duplicate` | Same-process simulation with an in-memory checkpointer; durable storage untested (disclosed) | — |
| S13 | Retries / circuit breaker | Max 3 attempts, 0.2→2 s jittered backoff, breaker after 5 consecutive failed calls, 30 s open | **Implemented; breaker untested** | `test_transient_fault_recovers…` covers retries; no breaker test | Add a breaker test or describe it as untested (V-15) | Low |
| S14 | Grounding | Every ID/number/date in the answer must appear in evidence; 1 retry then template | **Implemented + tested** | `test_grounding_retry_then_fallback`; 16 retries and 4 template fallbacks in the final run | Over-strict on derived values (disclosed) | — |
| S15 | Audit integrity | Append-only SQLite (update/delete triggers); 7 events per approval run | **Implemented; append-only untested** | `audit.py` triggers; event sequence asserted in `test_approve_executes_exactly_once_and_verifies` | Add a test that UPDATE/DELETE fail | Low |
| S16 | Sensitive data in traces/logs | Bank accounts masked at the service; JWTs never logged | **Implemented** | Published logs: 0 JWT-like strings, 0 API keys, 0 unmasked vendor bank numbers. Logs do contain tool outputs (synthetic invoices, vendor names, the injected attacker strings) | Production: redact or minimise tool outputs in logs and traces | Low |
| S17 | Authentication | HS256 JWT with signature, issuer, expiry, required claims | **Implemented (synthetic)** | `test_token_roundtrip_expiry_tamper` | No audience check, shared test secret, no gateway, no revocation (disclosed in article §6) | — (disclosed) |

**Unimplemented production assumptions** (must stay labelled as such in the article): authenticated approval channel (S6);
audience validation, revocation and refresh; identity-provider-derived tenant context; on-behalf-of token exchange to real
APIs; downstream enforcement of user scope; durable checkpointer; re-authorisation and approver-reason validation before
execution; business-level de-duplication; secret manager; log redaction; throughput and load testing; adaptive injection.
